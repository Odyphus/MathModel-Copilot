# Stage 7 — 模型评价、改进与推广边界

**时长**: 1-2h | **反馈层**: L1

## 目标

把 Stage 5/6 的证据转化为可信的模型评价：哪些能力已经被实验支持，哪些限制会影响结论，怎样验证改进，以及迁移到新场景时必须重新标定什么。评价质量取决于证据与影响范围，不取决于条目数量。

## 输入

- Stage 5 各子问题的结果、基线比较、代码与失败记录
- Stage 6 的验证域、定量结果、失败边界与 L2 回检
- 决策日志中的假设、被拒方案和未解决问题

## 产出

- 有出处的优点
- 有证据、影响范围和替代方案的局限
- 可执行且可验证的改进路线
- 适用条件清楚的推广场景；若没有可信迁移对象，则明确不主张推广
- 写入 `decision_log.stages.7`

## 操作流程

### Step 1：只保留有证据的优点（20 min）

每条优点使用以下结构：

```text
能力：<模型在哪个方面表现好>
证据：<结果表、基线实验、理论性质或 Stage 6 记录>
适用范围：<数据、参数域、规模或场景>
不能推出：<证据尚未支持的更强结论>
```

示例：

```text
能力：在已测试实例上保持可行。
证据：Stage 6 的所有压力场景均满足约束 C1-C4，见 results/feasibility.csv。
适用范围：只覆盖报告中的需求与容量范围。
不能推出：范围外仍可行，或该方案在所有实例上最优。
```

运行时间、精度、稳健性或“优于基线”的陈述必须能定位到真实实验。没有比较实验时，改写为设计特征，不写成性能优势。

### Step 2：从证据缺口提炼局限（35 min）

每条局限回答五个问题：

```text
局限：<具体假设、数据缺口、算法边界或验证不足>
证据：<观察、失败样本、残差、未覆盖范围或理论条件>
影响：<哪些结果、场景或决策可能受影响>
替代/改进：<具体方法或新增数据>
验证计划与代价：<怎样比较；需要的时间、数据或算力>
```

若替代方法尚未实现，`observed_gain` 必须为 `null`。只有完成同数据、同指标、同切分的对照实验后，才能填写改进幅度，并附结果文件。

可信示例：

```text
局限：需求分布只在训练期内估计。
证据：按时间留出后，后两期残差方差明显增大，见 figures/residual_by_period.png。
影响：长期容量建议可能低估尾部风险。
替代/改进：比较负二项模型与分布鲁棒方案。
验证计划与代价：保持同一时间切分，比较校准误差和决策成本；需要重新拟合并重跑 Q3。
observed_gain：null（尚未完成对照实验）。
```

不要为了凑条目重复同一限制，也不要填写任何没有对照实验来源的提升数字。

### Step 3：把改进写成可执行实验（20 min）

每个改进项至少包含：

- 要修复的局限；
- 代码、数据或模型的具体改动；
- 对照基线、数据切分和评价指标；
- 资源需求与停止条件；
- 当前状态：`planned | tested | adopted | rejected`；
- 已观察收益：有实验则填写数值和证据路径，否则为 `null`。

示例：

```json
{
  "name": "比较负二项与当前计数模型",
  "addresses": "留出期过度离散",
  "path": "复用同一时间切分，重估参数并重跑 Q3",
  "metric": "留出期对数似然、校准误差、决策成本",
  "resource_need": "一次重新拟合和一次完整求解",
  "status": "planned",
  "observed_gain": null,
  "evidence": []
}
```

### Step 4：验证推广，而不是罗列领域（15 min）

只有存在结构相似性时才提出推广。每个场景写清：

```text
场景：<新问题>
可复用：<数学结构、算法或软件组件>
必须重标定：<参数、数据分布、约束、损失函数>
新增风险：<原题不存在的机制>
最低验证：<迁移前必须完成的测试>
```

如果无法说明这些内容，写“当前证据不足以主张跨场景推广”。这比空泛列出多个领域更可信。

### Step 5：可信度自检（15 min）

逐条检查：

- 每个性能陈述能否定位到结果文件或理论依据；
- 局限是否说明受影响的结论，而非只写“假设理想化”；
- 所有改进幅度是否来自可复现实验；
- `planned` 的改进是否被误写成已实现；
- 推广是否包含重新标定与最低验证；
- 是否遗漏 Stage 6 的失败样本或未测试区域。

发现证据不足时，降级措辞、补实验或删除主张，不用更强的形容词掩盖缺口。

### Step 6：写入状态（10 min）

```json
{
  "strengths": [
    {
      "name": "...",
      "evidence": ["results/...", "paper §..."],
      "scope": "...",
      "non_claim": "..."
    }
  ],
  "limitations": [
    {
      "name": "...",
      "evidence": ["..."],
      "affected_claims": ["..."],
      "alternative": "...",
      "validation_plan": "...",
      "cost": "...",
      "observed_gain": null
    }
  ],
  "improvements": [
    {
      "name": "...",
      "status": "planned | tested | adopted | rejected",
      "path": "...",
      "metric": "...",
      "observed_gain": null,
      "evidence": []
    }
  ],
  "generalizations": [
    {
      "scenario": "...",
      "reusable_structure": "...",
      "recalibration": "...",
      "new_risks": "...",
      "minimum_validation": "..."
    }
  ]
}
```

空数组是允许的，但必须在正文说明为何没有足够证据支持该类主张。

## L1 Rubric

| 维度 | 满分行为 |
|---|---|
| 1. 优点具体 | 每项都有证据路径、适用范围和不外推声明 |
| 2. 局限真实 | 覆盖证据、受影响结论、替代方案与验证代价 |
| 3. 改进可执行 | 有对照设计、指标、资源、状态；未测试时不填收益 |
| 4. 推广具体 | 说明可复用结构、重新标定、新风险与最低验证，或诚实不主张推广 |
| 5. 自我批判可信 | 不隐瞒失败样本，不把计划当结果，不虚构提升幅度 |

## 常见坑

- H1：套话式局限 → 补证据、影响范围和验证计划
- H2：优点夸大 → 降级为已观察事实并标注测试域
- H3：推广空泛 → 写重新标定和最低验证，或删除推广主张
- H4：计划性收益写成已实现 → 将 `observed_gain` 设为 `null`

## 退出条件

1. 所有性能与改进幅度都有可复核证据；
2. 核心局限说明了受影响的结论和验证路线；
3. 改进项区分计划、测试、采用与拒绝状态；
4. 推广包含迁移条件，或明确当前不主张推广；
5. L1 全维达到工作流阈值。
